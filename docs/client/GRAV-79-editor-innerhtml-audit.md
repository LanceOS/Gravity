# GRAV-79: editor HTML ingress and `innerHTML` audit

Audited against `e430a96a` (main, 2026-10-15). Scope: client and library editor source, the rendered comment path, locked ProseMirror dependencies, relevant note/ticket persistence boundaries, and a fresh production build. This is an inventory and risk assessment; it does not change sanitization behavior. Current-risk labels describe what the evidence establishes, separately from the impact if an existing guard were removed.

## Executive findings

- **Confirmed unsafe DOM attributes from shared notes; execution unproven.** [richText.ts:72-85](../../library/utilities/richtext/richText.ts#L72) accepts ProseMirror JSON without validating link `href` or image `src`; [useRichTextEditor.ts:99-100,132-142](../../library/components/richtext/hooks/useRichTextEditor.ts#L99) hands it to `EditorView`. An authenticated project member can submit such JSON through the notes API: its contract enforces size/depth limits but no URI policy ([contracts.ts:10-25](../../server/src/modules/notes/contracts.ts#L10)), and create/update persist the body as supplied ([notes.ts:23-44,93-125](../../server/src/modules/notes/services/notes.ts#L23)). A shared note is readable by another project member ([policy.ts:7-13](../../server/src/modules/notes/policy.ts#L7)). A source-based JSDOM check using the actual `parseRichTextValue`, schema, and `EditorView` confirmed an anchor with `href="javascript:alert(1)"` and an image with a `data:` URL in the editor DOM. This is a **medium-severity, high-priority validation gap**; browser execution, link activation behavior, and CSP bypass were not demonstrated. The default app-shell CSP has `script-src 'self'` and `img-src 'self' https:` ([app.ts:27-43](../../server/src/app.ts#L27), [nginx.template.conf:10](../../client/nginx.template.conf#L10)), which constrains those example URLs when applied. Trusted Types does not validate URL attributes. Ticket/comment writes use a separate server sanitizer.
- **High-impact paste guards are present, with a native fallback gap.** The app's browser `paste` handler sanitizes `text/html` before [its assignment at useRichTextEditor.ts:185](../../library/components/richtext/hooks/useRichTextEditor.ts#L185). Programmatic paste and external HTML drops run the [line 147 transform](../../library/components/richtext/hooks/useRichTextEditor.ts#L147) before ProseMirror's parser assignment. But ProseMirror's `capturePaste` fallback first lets the browser paste into a **live offscreen contenteditable** and reads it 50 ms later (`node_modules/prosemirror-view/src/input.ts:672-685`); sanitization occurs after that read. Whether dangerous markup can survive the browser's native paste step is untested. Preserve the current guards and treat the fallback as a high-priority browser test target, not a proven exploit.
- **Image insertion has no local URI check.** [RichTextEditor.tsx:67-79](../../library/components/richtext/RichTextEditor.tsx#L67) inserts its caller's `src` into the model. The only located production caller supplies an upload URL ([NoteEditor.tsx:123-136](../../client/src/modules/notes/components/NoteEditor.tsx#L123)); this is a **low observed risk** for that caller, but the reusable API should validate untrusted future inputs. Notes persistence does not add URI sanitization on save.

## Ingress and rendering trace

1. **Native HTML paste with accessible `text/html`:** the application handler reads `clipboardData` ([useRichTextEditor.ts:167-169](../../library/components/richtext/hooks/useRichTextEditor.ts#L167)), prevents the browser default, sanitizes through DOMPurify, then assigns the resulting `TrustedHTML` or sanitized string to a detached container and parses a ProseMirror slice ([lines 171-187](../../library/components/richtext/hooks/useRichTextEditor.ts#L171)). ProseMirror runs custom DOM handlers before its own paste handler (`node_modules/prosemirror-view/src/input.ts:46-52,84-88`). The generic sanitizer removes `data-pm-slice`; a direct sanitizer check returned `<p><a>test</a></p>` from a payload with a slice marker, event handler, and `javascript:` link. This is a copy/paste fidelity difference from the separate clipboard sanitizer, not evidence of XSS.
2. **Plain text and rejected HTML:** when sanitization empties HTML, the app calls `view.pasteText` for a supplied `text/plain` value and consumes the event ([useRichTextEditor.ts:173-178](../../library/components/richtext/hooks/useRichTextEditor.ts#L173)). Plain-text ProseMirror parsing constructs text/paragraph nodes rather than assigning HTML (`node_modules/prosemirror-view/src/clipboard.ts:47-65`).
3. **Native fallback:** if the custom handler cannot read HTML, ProseMirror may handle plain text directly, or use its `capturePaste` target when clipboard data cannot be processed (`node_modules/prosemirror-view/src/input.ts:672-720`). That target is appended to the live document and focused before native paste. ProseMirror removes it after 50 ms, reads its `innerHTML`, and only then calls `doPaste`, whose HTML branch invokes the app's transform (`node_modules/prosemirror-view/src/clipboard.ts:67-69`). If the app receives no HTML while composition is active, ProseMirror can also leave the native paste to the browser (`input.ts:708-715`). The exact dangerous-markup behavior of these browser-managed branches was not tested.
4. **Programmatic paste and drops:** `EditorView.pasteHTML` goes to `doPaste` (`node_modules/prosemirror-view/src/index.ts:437-442`), then `parseFromClipboard`, the app transform, and the dependency `readHTML` assignment. An external drop carrying HTML takes that same parser route (`input.ts:782-793`). An internal drag carrying `dragging.slice` skips HTML parsing and the transform; it can move preexisting unsafe model attributes.
5. **Stored values:** authenticated project members can create or update notes ([routes.ts:15-23,30-44,140-161](../../server/src/modules/notes/routes.ts#L15)). The API accepts a shared note body with unsafe-URI ProseMirror JSON, saves that body, and returns it on read ([notes.ts:23-51,74-90](../../server/src/modules/notes/services/notes.ts#L23)). [NoteEditor.tsx:24-34,145-157,348-357](../../client/src/modules/notes/components/NoteEditor.tsx#L24) preserves JSON and supplies it to `RichTextEditor`. [richText.ts:72-85](../../library/utilities/richtext/richText.ts#L72) deserializes it, and `EditorView` writes schema-derived URL attributes to live DOM. This also applies to the editor's external-value replacement ([useRichTextEditor.ts:99-126](../../library/components/richtext/hooks/useRichTextEditor.ts#L99)) and read-only mode (line 144 only changes editability). By contrast, ticket descriptions and comments pass `sanitizeEditorContent` on new server writes ([tickets.ts:94-101,1047,1229,1448,1471](../../server/src/modules/tickets/services/tickets.ts#L94)); older values can still reach the same editor path.
6. **Legacy Markdown and display:** [richText.ts:68-69](../../library/utilities/richtext/richText.ts#L68) parses non-JSON values with `prosemirror-markdown`'s default Markdown-it parser, configured with `html: false` (`node_modules/prosemirror-markdown/src/from_markdown.ts:243-245`). A direct parser check kept `[click](javascript:alert(1))` as literal text. The comment display path instead serializes the model, sanitizes HTML, assigns it to a detached template, and projects elements into React ([richText.ts:130-144](../../library/utilities/richtext/richText.ts#L130), [MarkdownContent.tsx:292-318](../../client/src/modules/tickets/components/MarkdownContent.tsx#L292)). Ticket descriptions are rendered by the editor, not by this template.

## Timing, browser policy, and performance

- The normal app paste path calls DOMPurify and performs its `innerHTML` assignment synchronously after `preventDefault`; there is no asynchronous gap between those steps. The clipboard-specific sanitizer installs a temporary DOMPurify hook and removes it in `finally` in the same call stack ([sanitize.ts:151-165](../../library/utilities/sanitize.ts#L151)). No cross-event hook race was found in the single browser JavaScript realm. The **50 ms native capture target** is the material timing exception.
- The production app-shell CSP includes `script-src 'self'`, `img-src 'self' https:`, and Trusted Types enforcement ([app.ts:27-43](../../server/src/app.ts#L27), [nginx.template.conf:10](../../client/nginx.template.conf#L10)). Those directives constrain the example `javascript:` and `data:` URLs when enforced, but the audit has no real-browser execution or CSP-bypass result. Trusted Types protects HTML assignments, not schema-generated `href`/`src` attributes. The example image URL's presence in DOM does not show a network request or script execution.
- `MarkdownContent` sanitizes twice and memoizes by `text` and ticket regex ([MarkdownContent.tsx:292-312](../../client/src/modules/tickets/components/MarkdownContent.tsx#L292)); this is extra work per changed comment, not a measured performance regression. It creates a detached serializer DOM before sanitizing the resulting HTML, so browser resource-load side effects from a source attribute were not ruled out. The editor already skips reparsing its own unchanged serialized value ([useRichTextEditor.ts:93-110](../../library/components/richtext/hooks/useRichTextEditor.ts#L93)). A fix can validate model attributes at note persistence and when loading an external value, without running a full HTML sanitizer on each editor transaction. No benchmark was run.

## Validation and next steps

- Targeted client tests: **198 passed** across `richtext-paste-xss`, `richtext-clipboard`, `sanitize`, `RichTextEditor`, and `MarkdownRenderingSecurity` using Node 22.23.3.
- `npm run build:client`: **passed**; generated assets inspected as above.
- A one-off JSDOM check importing the **actual** `parseRichTextValue` and schema, then mounting `EditorView`, confirmed that JSON with `javascript:` link and `data:` image attributes survives parsing and appears in the editor DOM. A separate direct call to `validateNoteRequest` accepted that JSON as a shared note body. Neither check saved a note through the API, executed a link, or exercised browser CSP.
- The browser Trusted Types acceptance script was not completed in this sandbox: its isolated dependency setup failed while spawning `git` (`EPERM`). The existing script covers paste, drop, CSP, and Trusted Types behavior at [editor-trusted-types-browser-test.mjs:107-229](../../client/scripts/editor-trusted-types-browser-test.mjs#L107); rerun it in a browser-capable CI environment before changing these guards.

**Recommended follow-up:** apply the shared URI policy to note JSON at persistence and before initial editor construction or external value replacement; validate `insertImage` inputs as the API gains callers. Preserve the two existing paste sanitizers and add regressions for normal HTML paste, programmatic paste, external drops, and the native capture/composition branches in real browsers. Test unsafe stored links with production CSP before assigning an XSS severity. GRAV-80's premise should be reconciled with the already-present clipboard sanitizer before implementation work starts.

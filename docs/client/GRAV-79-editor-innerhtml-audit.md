# GRAV-79: editor HTML ingress and `innerHTML` audit

Audited at `e430a96a` (main, 2026-10-15). Scope: the client and library editor runtime, its rich-text display path, the locked ProseMirror dependency, and a fresh production build. This is an inventory and risk assessment; it does not change sanitization behavior.

## Executive findings

- **High priority — stored document editor rendering:** [richText.ts:72-85](../../library/utilities/richtext/richText.ts#L72) accepts syntactically valid ProseMirror JSON without validating link `href` or image `src`. [useRichTextEditor.ts:99-100,132-142](../../library/components/richtext/hooks/useRichTextEditor.ts#L99) passes that document to `EditorView`, which renders those attributes directly. This path does **not** use `innerHTML`, but it is an untrusted-to-DOM route that an `innerHTML`-only search would miss. The notes API accepts such JSON without URI sanitization ([contracts.ts:10-25](../../server/src/modules/notes/contracts.ts#L10), [notes.ts:23-44,93-125](../../server/src/modules/notes/services/notes.ts#L23)); a shared note is readable by another workspace member ([policy.ts:7-13](../../server/src/modules/notes/policy.ts#L7)). A local source-schema reproduction with `nodeFromJSON` and `EditorView` produced an anchor with `href="javascript:alert(1)"` and an image with a `data:` URL. The source schema is the unmodified `prosemirror-schema-basic` link/image schema ([rich-text-schema.ts:5-9](../../server/src/lib/rich-text-schema.ts#L5)); it checks types, not URI safety. Ticket/comment writes are sanitized separately. Treat the unsafe anchor as a potential XSS on link activation; the proof establishes DOM insertion, not script execution.
- **High priority to preserve — HTML paste and drop:** both paste routes currently sanitize before their HTML parser sinks. The browser `paste` handler uses `sanitizeTrustedHtml` before its [assignment at useRichTextEditor.ts:185](../../library/components/richtext/hooks/useRichTextEditor.ts#L185). Drops, programmatic `pasteHTML`, and ProseMirror fallback paste use `sanitizeRichTextClipboardHtml` at [line 147](../../library/components/richtext/hooks/useRichTextEditor.ts#L147) before ProseMirror's own `innerHTML` assignment. No unsanitized pasted HTML-to-`innerHTML` path was found in the current editor configuration. These are high-impact choke points: removing either guard would expose untrusted clipboard HTML immediately.
- **Medium priority — image insertion API:** [RichTextEditor.tsx:67-79](../../library/components/richtext/RichTextEditor.tsx#L67) inserts the caller's `src` directly into a ProseMirror image node, without client URI validation. The only located production caller uses an uploaded media URL ([NoteEditor.tsx:123-136](../../client/src/modules/notes/components/NoteEditor.tsx#L123)). Keep this method restricted to trusted URLs or validate `src` before creating the node; server sanitization occurs only on save.

## Validation and next steps

- Targeted client tests: **198 passed** across `richtext-paste-xss`, `richtext-clipboard`, `sanitize`, `RichTextEditor`, and `MarkdownRenderingSecurity` using Node 22.23.3.
- `npm run build:client`: **passed**; generated assets inspected as above.
- A one-off JSDOM check using the same ProseMirror schema and `EditorView` confirmed that JSON with `javascript:` link and `data:` image attributes survives schema parsing and appears in the editor DOM. This did not execute the link.
- The browser Trusted Types acceptance script was not completed in this sandbox: its isolated dependency setup failed while spawning `git` (`EPERM`). The existing script covers paste, drop, CSP, and Trusted Types behavior at [editor-trusted-types-browser-test.mjs:107-229](../../client/scripts/editor-trusted-types-browser-test.mjs#L107); rerun it in a browser-capable CI environment before changing these guards.

**Recommended follow-up:** sanitize or validate ProseMirror JSON URI attributes at note persistence and before initial editor construction or external value replacement; validate `insertImage` URLs at the client boundary. Preserve the two existing paste sanitizers and add a regression that asserts they run before both application and ProseMirror HTML assignments. GRAV-80's premise should be reconciled with the already-present clipboard sanitizer before implementation work starts.
